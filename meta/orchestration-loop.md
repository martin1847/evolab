# 编排回路（orchestration-loop）

> **Goal → Action → Evidence → Eval → Feedback**：选题与合同 → 执行与派工 → 取证与回执 →
> 评审与门 → 复盘与规则回写，一圈闭合才算一次交付。本篇 = 骨架索引 + **两条诊断层判据**
> （环的强弱怎么判、诊断取证要双源）；**不新增任何环内规则、不新增门**——各环规则仍住
> 各正源里，这里只管「病归哪环、哪环该先治」。
> NS-1 四短语（`orchestrator-core` §0）是本回路的系统级压缩；本篇把粒度铺开，不替代它。

## 五环定义（病往环上归，处方跟环走）

- **Goal（选题与合同）**：投什么面、给谁写合同。病形：合同缺条款则 worker 自造判据、
  选题权被评审输出接管（上一轮制造的表面变成下一轮的任务）、真实用户路径从未被走通。
- **Action（执行与派工）**：worker 行为、lane 运行、进程与会话卫生。病形：执行漂移、
  孤儿进程、跨席位误伤、在错误的树上取证。
- **Evidence（取证与回执）**：回执真实性与证据形态。病形：回执撒谎、证据被管道截断、
  缺口是散文进不了决策、否定性断言无探针。
- **Eval（评审与门）**：冷评审、测试门、guard 及它们的自证。病形：门测错对象 / 量纲错 /
  因错误理由而绿、同源陷阱、只亮绿灯的门 = 没有门。
- **Feedback（复盘与规则回写）**：教训分诊、升层、淘汰。病形：复盘仪式空转、教训沉淀成
  散文后原样复发、advisory 只攒不清。

## 既有实例互认（同一骨架的不同粒度展开）

| 粒度 | 实例（正源） | 覆盖段 |
|---|---|---|
| 系统级 | NS-1 四短语（`orchestrator-core` §0） | 全环压缩 + Eval 定期攻击 workflow |
| 单次派工 | `cto-orchestration` §1 派工闭环 | Goal→Action→Evidence→Eval |
| 单面投入 | `leverage-line` 信号→分诊→裁决 | Eval→Feedback |
| 批次收口 | `cto-orchestration` retrospective 七步 + 晋升三门 | Feedback→Goal |
| 单轮评审 | `heterogeneous-cold-review` 收敛与止损 | Eval→Feedback |

这些实例此前互不指认；把它们认作同一骨架后，跨粒度的病才能对上号——例如「教训复发」
（复盘粒度）与「不 fire 的散文是净负债」（规则粒度）是同一病在两层的投影。

## 诊断用法：环的强弱不看病的条数，看对策的形态

判哪环薄弱，判据是**对策失效率**，不是病历数量：某环的对策一直停留在散文 / 提醒档，
且有「对策已装仍复发」的记录，它就是最薄的环——病多而对策带电的环反而是健康的
（病被看见、被拦住）。对策形态阶梯见 `structure-not-discipline`（L0→L1→L2）；
「教训要与门同形态」的电在 `cto-orchestration` retrospective §教训分层沉淀 + retro-check。

诊断取证必须**双源**：外部事故报告与内部评审发现的落点几乎不重叠（多席位实证：前者集中
Evidence / Action，后者集中 Eval / Goal）——任一来源单用都有系统性盲区，这是同源陷阱
（`truth_not_eq_checker_output`）在编排层的实例。

## 已指认的薄点（按证据升级，不预置处方）

- **Goal 段是 meta 层唯一零覆盖段**：选题与合同的反思只活在 goal-template /
  review-dispatch 的操作层，尚无范式层文档。补不补，等病历攒够再定。

## 来源

一次五环全量考古（多编排席位、跨两月提交史与事故信归档）收敛出上表与诊断判据：
Feedback 环被判最薄的依据正是「对策 = 更多散文」且复发白纸黑字（同一教训沉淀后
原样复发 ≥2 例、复盘提醒真 fire 而行为未发生）；Eval 环病历最多却最健康——几乎每例
都被评审或门当场拦下。诊断当日即把 Feedback 环的对策升形态（typed 教训行入 retrospective）。
