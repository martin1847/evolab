# 筛选：原始笔记 → 有人会去处理的清单

自己在编排上下文里对子代理的原始产出做这一步。不要交回探索者：finding 的作者是「它是不是真的」
最差的裁判。

探索性 pass 天然多报。这是对的——一个神经紧张的探索者正是目的。这道过滤器让多报不至于变成噪声。

## 1. 删，按此顺序

删除是默认动作。每条规则独立成立；命中一条即够。

1. **无证据。** 缺 URL、缺逐字引文、或截图路径在磁盘上不存在。不要回去补——事后重建的 finding
   是记忆，不是观察。
2. **推测。** 任何写成「可以 / 也许 / 应该 / 要是…更好 / 用户可能」的东西。以及任何关于探索者没走到的
   屏幕的东西。
3. **伪装成 finding 的建议。** 如果这条「finding」是一个提议的改动外加一句抱怨，删。只有能把它
   纯粹重述成「在第 X 步我期待 A，看到 B」且仍然成立时才留。
4. **命中 glossary。** 这个词配置里定义过。不认识它是探索者的缺口，不是产品的。
5. **环境伪影。** 因为本地栈被灌了假数据、fake 掉、迁移了一半或离线而坏掉的东西——真用户永远
   不会遇到。诚实判断：真用户**也会**撞上的错误页要留。
6. **自找的。** 探索者输了胡话、跳过了被告知的必填项、或在跟浏览器工具较劲。

## 2. 并

同一个根源瞬间报了两次（一次 `blocked` 一次 `confused`；或同一个缺失标签在两个屏幕各见一次）
→ 合成一条，`blocked` 胜出，保留最强的证据，两个屏幕都列进 `reproduce`。

## 3. 排

按它挡住一个想走完旅程的人的程度：

1. 硬停，无路可走。
2. 停住，但用户靠猜找到了绕法。
3. 走过去了，但不知道成没成。
4. 走过去了，懂了操作，没懂含义。

同档按旅程步靠前者优先——大门口的一堵墙比最后一个房间的同一堵墙多挡得多的用户。

## 4. 封顶并说明代价

留前 10 条。存活的更多就在 Markdown 里明说（`N 条通过筛选；列出最挡路的 10 条`）——被静默截断的
清单读起来像「就这些了」。

也记下你删了什么：JSON 里的 `triage` 块（原始条数、存活条数、每条掉落一行写触发了哪条规则），
Markdown 底部同一张表。没有 triage 块的清单分不清是「筛过」还是「什么都没删」，而掉落项往往是
一次 pass 最有意思的产出——两条以「环境伪影」被删本身就是新闻：环境探不了产品的那一部分。

同样把 `steps_not_reached` 带进 Markdown。pass 没走到的步是报告里最不可信的部分，只有说出来
才能让其余部分可信。

## 5. 发出前自检

- 每条存活 finding 通过 `output-schema.json` 校验。
- 每个 `step` 是配置 `journey` 里的 id，不是编的。
- 每个截图路径存在。
- 没有 finding 含「应该」。
- 至少一条 finding 能被一个人按 `reproduce` 逐字复现。哪条都说服不了自己 → 这次 pass 失败了，
  照实说，别交一份没人能处理的清单。
